# ADR-0004: Per-case storage layout

Status: accepted · 2026-10-20

## Context

Kagegami keeps engagement state (hosts, services, credentials, findings, journal) in SQLite and raw tool output on disk. We had to decide whether that state is shared or separated per engagement, how the active engagement is chosen, and a few conventions for timestamps and logs.

## Decision

### One directory and one database per case

Each case ("engagement") lives in its own directory under the data directory defined in ADR-0001:

```
<data>/
  cases/
    <name>/
      kagegami.db     # SQLite state for this case only
      raw/            # raw command output, one file per output blob
  logs/               # application logs (not per case)
```

Why: cases are isolated, can be archived or deleted by removing one directory, and credentials from different engagements never sit in the same file. This also matches client NDAs that require data for one client to be kept apart from another's.

Case names are restricted to `[A-Za-z0-9._-]`, must not start with a dot, and are validated before being joined to a path, so a name can never escape `<data>/cases/`.

### The active case is always explicit

The case is selected with the `--case <name>` flag or the `KAGEGAMI_CASE` environment variable; the flag wins. If neither is set, commands that need a case fail with a clear error (`no case selected: pass --case or set KAGEGAMI_CASE`). There is no implicit "last used case". A security tool should not guess which engagement it writes to; a wrong guess would put data into another client's case.

`kagegami init` without `--case` only sets up the global config and templates. `kagegami init --case <name>` additionally creates the case directory and database.

### Timestamps are UTC milliseconds

All stored timestamps (`created_at`, `ts`, ...) are integer Unix milliseconds in UTC, generated by the application. Sorting and comparison are plain integer operations. Because the same case may be worked on from machines with different clocks (for example a Mac host and a Kali VM), the clock is a known weak spot: timestamps are never taken from parsed tool output as if they were ours, and entries record which source they came from.

### Logs

One log directory, `<data>/logs/`, next to `cases/`. XDG state is deliberately not used, to avoid a third XDG category for a single-user tool.

### Configuration

The config schema accepts every key from the design document up front, plus `logging.level`. Unknown keys are an error, so typos fail at startup instead of being silently ignored.

## Consequences

- The store opens one database per case; there is no cross-case query. Cross-case features, if ever needed, must open several databases explicitly.
- Every command that touches state needs case selection in the CLI layer, and the path resolver needs a validated `CaseDir(name)`.
- File permissions follow ADR-0001: directories `0700`, files `0600`.
